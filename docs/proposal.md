一、專案簡介
Typing Paws(2.0版本，因為作業五的是1.0) 是一個結合生成式AI的英文打字練習遊戲。作業五我做出了單檔版的《喵喵打字大冒險》（https://ctycet.github.io/typing-paws/Links to an external site.Links to an external site.），玩家透過打字攻擊怪物。期末專案會把它擴充成完整的網站，讓AI根據每位玩家的打字弱點自動出題、即時生成故事和怪物，並加入帳號、雲端紀錄、排行榜與對戰功能。
 
二、動機：現有打字練習網站的問題
1. 題目固定：不管哪個字母常打錯，練的都是同一批單字，練不到弱點。
2. 沒有長期回饋：只看到單場WPM，不知道自己哪裡在進步、哪裡卡住。
3. 很快就膩：重複的文本加上沒有目標，難以持續練習。
我的想法是利用LLM依弱點「量身出題」，用故事和遊戲化維持動機，再用數據儀表板呈現進步。
 
三、作業五→期末專案的差異
・題目來源：內建固定字庫→內建字庫＋LLM 個人化生成
・遊戲模式：三關闖關 → 闖關、AI 故事模式、弱點特訓、每日挑戰、雙人對戰
・怪物：emoji → AI 生成立繪＋AI 生成名字與台詞
・紀錄：只存在瀏覽器 → 帳號登入、雲端保存、跨裝置
・分析：單場WPM → 鍵盤熱力圖、長期趨勢、AI學習建議
・技術：單一index.html→React 前端＋Supabase 後端＋AI API

五、核心功能
A. 弱點特訓（LLM）— 主要功能
・記錄每次按鍵的對錯與間隔時間，統計每個字母、每個字母組合（如 th、qu）的錯誤率與反應時間。
・找出最弱的 3～5 個字母或組合，連同難度、主題組成 prompt，請 LLM 生成單字與句子，並要求以 JSON 格式回傳。
・前端／後端驗證生成結果：只允許英文字元、檢查長度、過濾不當用字；不合格就重試，失敗則改用內建字庫，確保遊戲不會中斷。
B. AI 故事模式（LLM）
・玩家選主題（奇幻、太空、校園），LLM 一次生成一章短故事，玩家把段落打完才能推進劇情。
・打字表現影響劇情：高 Combo 走勝利路線，失誤太多會觸發危機劇情，讓每次遊玩的故事都不一樣。
C. AI 生成怪物（圖像生成＋LLM）
・用 text-to-image 模型（如 Stable Diffusion／FLUX）生成可愛風格的怪物立繪，LLM 生成怪物名字、台詞與弱點屬性。
・為了成本與穩定度，先批次生成一批怪物存在雲端，遊戲中直接讀取；「玩家輸入描述生成自己的怪物」為進階功能。
D. 帳號與雲端紀錄
・Google 登入，所有成績與按鍵統計存在資料庫，換電腦也能延續進度；保留訪客模式（只存本機）。
E. 數據儀表板
・鍵盤熱力圖（每個鍵的錯誤率）、WPM／準確率趨勢圖、弱點排行，以及 LLM 根據數據寫的每週學習建議。
F. 每日挑戰與雙人對戰（加分功能）
・每日挑戰：全部玩家打同一段文本，比排行榜。
・雙人對戰：建立房間，透過即時連線同步雙方進度，先打倒怪物的人獲勝。
 
六、系統架構與使用技術（見圖二）
・前端：React + TypeScript + Vite，沿用作業五的遊戲邏輯與動畫並拆成元件；Chart.js 畫圖表。
・後端：Supabase
─ Auth：Google 登入
─ PostgreSQL：成績、按鍵統計、題庫快取、排行榜
─ Realtime：雙人對戰同步
─ Storage：AI 生成的怪物圖片
─ Edge Functions：AI 閘道，負責保管 API 金鑰、組 prompt、驗證輸出、限制每人每日呼叫次數
・生成式 AI：LLM API 負責文字生成（題目、故事、怪物設定、學習建議）；text-to-image 模型負責怪物立繪。
・部署：前端放 GitHub Pages 或 Vercel，後端用 Supabase 免費方案，GitHub Actions 自動部署。
・設計重點：API 金鑰只放在後端，前端不直接呼叫 AI 服務，避免金鑰外洩。

七、生成式AI的應用細節（見下面的圖三）
流程：玩家打字 → 記錄按鍵資料 → 弱點分析 → 組成 prompt → LLM 生成題目 → 驗證後存入題庫 → 回到玩家打字。
 
prompt 範例（精簡）：
「你是英文打字教練。請生成 15 個單字與 5 個短句，必須大量包含 "q"、"z"、"th"，難度中等（5～9 個字母），主題是太空冒險。只輸出 JSON：{ "words": [...], "sentences": [...] }」
 
會用到的課程概念：
・Prompt 設計：角色設定、限制條件、指定輸出格式（JSON）。
・控制生成結果：調整 temperature 讓題目有變化又不離題；用驗證規則處理 LLM 偶爾輸出不合格的內容。
・圖像生成：設計固定的風格提示詞（貼紙風、粗外框、可愛），讓不同怪物的畫風一致。

八、可行性評估與備案
・LLM回傳格式錯誤或API失敗 → 自動重試一次，仍失敗就用內建字庫，遊戲不中斷。
・API費用 → 選用低成本模型、生成結果存入題庫重複使用、每人每日次數上限。
・圖像生成速度慢、品質不穩 → 先手動批次生成約12隻怪物並挑選後上傳，即時生成列為進階功能。
・即時對戰較複雜 → 先完成「每日挑戰排行榜」（非同步比賽），有時間再做即時對戰。
・已驗證的部分：作業五已完成打字判定、Combo、關卡、紀錄與部署，核心玩法可行；新的部分主要是串接 API 與資料庫。
