# 自主模式的決定紀錄（DECISIONS）

階段 2（數據儀表板本機版）是在「自主模式」下連續做完的，原本需要先問的決定（資料結構、畫面外觀）
都記在這裡，方便事後一起檢查。每一條都寫了選了什麼、為什麼、如果要改會動到哪裡。

## 2.1 按鍵統計的資料結構與儲存介面

**D1. 存「每場、每個鍵一列」的彙整統計，不存每一次按鍵的原始紀錄。**
- 內容：`KeyStatRow`（`src/game/keystats.ts`）= 一場裡某個鍵或字母組合的 次數、錯誤數、計時次數、反應時間總和。
  戰鬥中每次按鍵的原始紀錄（`KeyEvent`）只留在記憶體，一場結束就彙整掉。
- 理由：一場大約 300～600 次按鍵，原始紀錄存 30 場會佔掉好幾 MB；localStorage 上限約 5 MB，而且和 1.0 共用同一個網域。
  儀表板、弱點分析要的都是「每個鍵的次數／錯誤率／平均時間」，彙整後的資料就夠了；ROADMAP 2.2 的完成條件也是
  「打完一場後 localStorage 多一筆場次統計」。
- 代價：之後如果想分析「把 a 打成 s」這種混淆配對，現有資料算不出來，要另外加欄位或資料表。

**D2. 存總和（`timedCount`、`totalMs`），不存平均或錯誤率。**
- 理由：總和可以跨場次直接相加，再除出平均；存平均的話合併多場時會算錯。搬進資料庫後也可以直接 `SUM()`。

**D3. 扁平的列，欄位直接對應日後的 `key_stats` 資料表。**
- 欄位對照寫在 `src/game/keystats.ts` 開頭的註解。`sessionId` 就是 `GameRecord.id`（之後是 `game_records.id` 的外鍵）。
- `id` 用 `${sessionId}:${kind}:${key}` 組出來，是固定可重現的：之後訪客資料併入帳號（3.7）重複上傳時可以直接 upsert，不會重複。
- 本機沒有 `user_id`，上傳時由登入身分補上。

**D4. 英文字母一律轉小寫統計；字母組合（bigram）只算「兩個相鄰的英文字母」。**
- 理由：熱力圖是照實體按鍵畫的，`A` 和 `a` 是同一顆鍵；弱點特訓要給 LLM 的也是「哪些字母弱」。
  含空白、數字、標點的組合（例如 `t `、`4 `）對出題沒有幫助，而且種類很多，會讓資料量變大。
- 數字與標點仍然各自統計成 `char`（熱力圖會把 `!` 併到 `1` 那顆鍵上顯示）。

**D5. 只保留最近 30 場的按鍵統計（`KEY_STATS_SESSION_LIMIT`）。**
- 理由：和歷史戰績的上限一致，資料量有上限（估計整份 0.3～0.7 MB）。弱點分析本來就該看「最近」的表現，
  太久以前的弱點可能已經練好了。登入後雲端可以保留全部，這個上限只是本機的。

**D6. 儲存介面 `KeyStatsStore` 是同步的（local-first）。**
- 內容：`load()`、`saveSession(rows)`、`clear()`，localStorage 實作在 `src/storage/keyStats.ts`。
- 理由：畫面永遠讀本機這一份，遊戲不會因為網路慢或斷線卡住（CLAUDE.md 和 ROADMAP 3.5 都要求斷網不卡住）。
  日後 Supabase 是「同步的對象」：登入後把本機的列上傳、把雲端的列下載回來合併，而不是把這個介面換成非同步的。
- 如果階段 3 決定改成「雲端為主」：需要把介面改成回傳 Promise，並在 `App.tsx` 加載入中的狀態。

## 2.2 按鍵紀錄器

**D7. 按鍵紀錄寫在戰鬥 reducer 裡（`BattleState.keyLog`），間隔用 reducer 自己累計的 `activeMs` 算。**
- 理由：reducer 本來就知道「現在應該打哪個字元」，也本來就只在戰鬥進行中累計時間，所以暫停、倒數、過關訊息的時間
  自然不會算進間隔，不需要在 React 那邊另外處理時間戳。整個紀錄器是純函式，可以不靠畫面測試。
- 代價：時間的解析度是一個畫面更新（約 16 ms），而且單次更新最多算 100 ms（原本就有的防呆）。
  打字的間隔通常是 100～400 ms，這個誤差對「哪個鍵比較慢」的比較影響很小。

**D8. 每一關開始、暫停後繼續的第一鍵不算間隔（`intervalMs` 是 `null`）。**
- 理由：這一鍵前面隔著倒數或暫停，量到的是「回神的時間」不是打字速度。
- 完成條件「暫停期間的時間不算進間隔」由兩件事一起保證：暫停時 `activeMs` 不前進，而且暫停後第一鍵不計時。

**D9. 反應時間只算「乾淨的」按鍵：打對、上一鍵也打對、間隔不超過 2 秒。**
- 理由：打錯之後改對的那一鍵，時間裡混了「發現打錯」的反應；超過 2 秒多半是分心。把這些排除，平均才代表正常的打字速度。
- 次數與錯誤數不受影響，每一次按鍵都會算。

**D10. 錯誤率的算法：輪到某個鍵時的每一次按鍵都算一次「次數」，打錯就算一次「錯誤」。**
- 例：要打 `h`，先按錯兩次才按對 → `h` 是 3 次、2 次錯誤。統計記在「應該打的鍵」上，不是記在誤按的那個鍵上。
- 另一種算法是「每個位置只看第一次有沒有打對」，連續按錯不會重複計算。這裡選前者，因為和畫面上的準確率算法一致
  （準確率也是 打對的次數 ÷ 總按鍵數），玩家比較容易對得起來。

**D11. 清除紀錄會連按鍵統計一起清掉**，確認視窗的文字改成「最佳紀錄、歷史戰績和按鍵統計都會被刪除」。
- 理由：統計是掛在場次底下的（`sessionId`），場次清掉後留著統計沒有意義。

## 2.3 彙整、2.4 弱點分析

**D12. 彙整（`aggregateKeyStats`）就是把同一個鍵跨場次的列相加，再算錯誤率與平均反應時間。**
- 目前是「保留的 30 場全部等權重」。沒有做「越近的場次權重越高」，先求簡單、容易驗算；之後弱點特訓如果覺得反應太慢再加。

**D13. 弱點的定義（`findWeaknesses`，門檻都在 `WEAKNESS_DEFAULTS`，可以調）：**
- 資料不足：全部單鍵的次數加起來不到 100 次（大約 1～2 場簡單難度）→ 不判斷，畫面顯示引導文字。
- 樣本門檻：單鍵至少 8 次、字母組合至少 5 次才列入。組合出現的機會比單鍵少，所以門檻較低。
- 算弱點的條件（符合其一）：錯誤率 ≥ 8%，或平均反應時間 ≥ 同類整體平均的 1.35 倍（且至少有 5 次計時）。
- 排序分數 = 錯誤率 + 0.2 ×（比整體平均慢的比例）。也就是「錯誤」比「慢」重要：慢 50% 大約等於多 10% 的錯誤率。
- 最多列 5 個；單鍵和組合排在同一份榜單裡（同一個弱點可能同時以 `q` 和 `qu` 出現，這對出題反而是有用的訊息）。
- 空白鍵不列入：沒辦法針對空白出題。
- ROADMAP 寫「選出最弱的 3～5 個」：這裡的做法是「最多 5 個、只列真的過門檻的」，所以弱點少的人可能只有 1～2 個，
  完全沒有時回報「全部都很好」。硬湊滿 3 個會把其實不弱的鍵標成弱點，之後拿去出題反而沒有針對性。
- 8% 和 1.35 倍是憑經驗先訂的起始值，沒有實際玩家資料可以校正；試玩後如果覺得太嚴或太鬆，只要改 `WEAKNESS_DEFAULTS`。

## 2.5 儀表板頁面骨架與入口

**D14. 入口放在主選單「📈 我的戰績」標題的右邊，一顆黃色小按鈕「📊 數據儀表板」。**
- 理由：儀表板是戰績的延伸，放在戰績區最容易找到；主選單上方已經有勇者、模式、難度三排卡片，再加一排會太擠。
  沒有另外做網址路由（和現有的選單／戰鬥／結算一樣用畫面狀態切換），所以重新整理會回到主選單。
- 黃色（主要按鈕色）是為了和旁邊白色的「清除紀錄」區分，也讓新功能比較顯眼。

**D15. 儀表板的版面：最上面一排總覽數字（場數、通關、平均 WPM、平均準確率、統計按鍵數），下面依序是鍵盤熱力圖、趨勢圖、弱點排行。**
- 總覽格子沿用結算畫面數據格子的樣子（白底、粗外框、偏移陰影）。手機寬度變成兩欄。
- 「沒有資料」的定義是：沒有任何戰績，也沒有任何按鍵統計。這時只顯示一張引導卡片和「去打一場」按鈕。
- 從 1.0 匯入的舊戰績沒有按鍵統計：總覽和趨勢圖會有內容，熱力圖和弱點排行各自顯示「還沒有資料」的說明。

**D16. 新增 `scripts/verify-dashboard.mjs`：用 Playwright 真的打兩場（每次輪到 `e` 都先按錯一次、中途暫停 3 秒），
再核對 localStorage 的統計和儀表板上的數字，並截圖到 `.compare/dashboard/`。**
- 理由：單元測試用的是假計時器和假圖表，這支腳本補上「真的瀏覽器、真的時間、真的 canvas」這一段。

## 2.6 鍵盤熱力圖

**D17. 鍵盤配置用美式 QWERTY 的四排字元鍵加空白鍵，不畫 Shift、Enter、Tab 等功能鍵。**
- 理由：遊戲只會出可列印的字元，功能鍵永遠沒有資料，畫出來只是佔位置（手機寬度也塞不下）。
- 要按 Shift 的符號（`!`、`&`、`+`…）併到它所在的那顆鍵（`1`、`7`、`=`）；大寫字母在統計時就已經併到小寫。
  有測試檢查內建字庫的每個字元都找得到對應的鍵。

**D18. 顏色分 5 級，依錯誤率：低於 2%（綠）、2–5%（淡黃）、5–10%（黃）、10–20%（粉紅）、20% 以上（深粉紅、白字）。**
- 色票用專案原有的顏色（#d9f7ea、#fff0c4、#ffd166、#ff8fab），和難度標籤「簡單綠、普通黃、困難粉」是同一組語意，
  最深一級另外加了一個比 #f05d86 再深一點的 #e8456f，讓白字看得清楚。
- 用分級而不是連續漸層：比較容易對照圖例，測試和驗證腳本也能直接檢查「這顆鍵是第幾級」。
- 弱點分析的門檻是 8%，所以大致上「黃色以上」就是快要或已經算弱點的鍵。

**D19. 次數不到 5 次的鍵不上色（灰底虛線框），但移上去仍然看得到實際數字，並註明「次數太少，先不上色」。**
- 理由：只打過 1～2 次的鍵，錯一次就是 50%、100%，直接上深色會誤導。

**D20. 詳細數字顯示在鍵盤下方固定的一行說明，而不是浮動的小提示框。**
- 滑鼠移上去、鍵盤 Tab 到、手機點一下都會更新這一行；每顆鍵另外有 `title` 和 `aria-label`。
- 理由：浮動提示在手機上沒辦法靠滑鼠觸發，而且在螢幕邊緣容易被切掉；固定一行在三種操作方式下都一樣。
- 只有顏色不足以傳達資訊（色覺辨識），所以數字一定要能用文字讀到。

**D21. 熱力圖只顯示錯誤率，不另外做「反應時間」的切換檢視。**
- 理由：ROADMAP 2.6 的完成條件只要求錯誤率；反應時間已經出現在每顆鍵的說明文字和弱點排行裡。之後想加切換再加。

## 2.7 WPM／準確率趨勢圖

**D22. WPM 和準確率畫成上下兩張橫軸相同的折線圖，不畫在同一張圖的左右雙縱軸上。**
- 理由：兩個指標單位不同（字／分鐘 與 百分比）。雙縱軸的圖上兩條線的高低和交叉點完全取決於兩邊刻度怎麼訂，
  很容易讓人讀出不存在的關係（「準確率追過 WPM 了」）。分成兩張、橫軸對齊，一樣可以上下對照同一場的表現。
- ROADMAP 寫的是「圖表顯示歷史場次的兩條趨勢線」：兩條線都有，只是各自一張圖。如果你還是想要同一張圖，
  改 `src/components/PerformanceTrendChart.tsx` 就可以，資料整理（`performanceTrend`）不用動。

**D23. 兩張圖的線都是深紫色（和主選單的走勢圖一致），用底下的填色區分：WPM 是粉紅、準確率是淡紫；每張圖有自己的標題。**
- 原本想用「粉紅線＋綠線」區分兩個指標，但用色覺模擬檢查後，這兩個顏色對紅綠色弱的人幾乎分不出來。
  既然已經分成兩張有標題的圖，就不需要靠線的顏色辨認指標了。
- 點的顏色沿用 1.0 的慣例（綠＝通關、粉紅＝被打倒），另外加上形狀：通關是圓點、被打倒是三角形，不只靠顏色。
  主選單的小走勢圖維持 1.0 的樣子（只有顏色），沒有改。

**D24. 縱軸範圍：WPM 從 0 開始；準確率的下限取整十（最高 90%），上限固定 100%。**
- 理由：準確率通常落在 85～100%，如果從 0 開始畫，線會擠在最上面看不出變化；WPM 從 0 開始才能看出實際的幅度。
  準確率這張有面積填色但不是從 0 開始，面積大小不代表比例，只是和 WPM 那張保持同樣的樣子，數值要看縱軸刻度。

**D25. 範圍切換是兩段式的膠囊按鈕「最近 10 場｜全部（N 場）」，放在區塊標題右邊，預設是最近 10 場。**
- 「全部」指的是本機保留的全部場次（最多 30 場）。
- 橫軸是「第幾場」而不是日期：同一天可能玩很多場，用日期當橫軸點會疊在一起；日期時間顯示在滑鼠提示裡。
- 滑鼠在圖上任何高度都會選到最近的那一場（不用對準小圓點）；圖下方有「用表格看這些數字」可以展開，給不方便看圖的人。

**D26. 只有 1 場時也畫（只有一個點），不像主選單的走勢圖要 2 場才出現。**
- 理由：儀表板的其他區塊在 1 場後就有內容，趨勢圖單獨空著會很奇怪。
