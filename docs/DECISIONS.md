# 自主模式的決定紀錄（DECISIONS）

階段 2（數據儀表板本機版）是在「自主模式」下連續做完的，原本需要先問的決定（資料結構、畫面外觀）
都記在這裡，方便事後一起檢查。每一條都寫了選了什麼、為什麼、如果要改會動到哪裡。

## 2.1 按鍵統計的資料結構與儲存介面

**D1. 存「每場、每個鍵一列」的彙整統計，不存每一次按鍵的原始紀錄。**
- 內容：`KeyStatRow`（`src/game/keystats.ts`）= 一場裡某個鍵或字母組合的 次數、錯誤數、計時次數、反應時間總和。
  戰鬥中每次按鍵的原始紀錄（`KeyEvent`）只留在記憶體，一場結束就彙整掉。
- 理由：一場大約 300～600 次按鍵，原始紀錄存 30 場會佔掉好幾 MB；localStorage 上限約 5 MB，而且和 1.0 共用同一個網域。
  儀表板、弱點分析要的都是「每個鍵的次數／錯誤率／平均時間」，彙整後的資料就夠了；ROADMAP 2.2 的完成條件也是
  「打完一場後 localStorage 多一筆場次統計」。
- 代價：之後如果想分析「把 a 打成 s」這種混淆配對，現有資料算不出來，要另外加欄位或資料表。

**D2. 存總和（`timedCount`、`totalMs`），不存平均或錯誤率。**
- 理由：總和可以跨場次直接相加，再除出平均；存平均的話合併多場時會算錯。搬進資料庫後也可以直接 `SUM()`。

**D3. 扁平的列，欄位直接對應日後的 `key_stats` 資料表。**
- 欄位對照寫在 `src/game/keystats.ts` 開頭的註解。`sessionId` 就是 `GameRecord.id`（之後是 `game_records.id` 的外鍵）。
- `id` 用 `${sessionId}:${kind}:${key}` 組出來，是固定可重現的：之後訪客資料併入帳號（3.7）重複上傳時可以直接 upsert，不會重複。
- 本機沒有 `user_id`，上傳時由登入身分補上。

**D4. 英文字母一律轉小寫統計；字母組合（bigram）只算「兩個相鄰的英文字母」。**
- 理由：熱力圖是照實體按鍵畫的，`A` 和 `a` 是同一顆鍵；弱點特訓要給 LLM 的也是「哪些字母弱」。
  含空白、數字、標點的組合（例如 `t `、`4 `）對出題沒有幫助，而且種類很多，會讓資料量變大。
- 數字與標點仍然各自統計成 `char`（熱力圖會把 `!` 併到 `1` 那顆鍵上顯示）。

**D5. 只保留最近 30 場的按鍵統計（`KEY_STATS_SESSION_LIMIT`）。**
- 理由：和歷史戰績的上限一致，資料量有上限（估計整份 0.3～0.7 MB）。弱點分析本來就該看「最近」的表現，
  太久以前的弱點可能已經練好了。登入後雲端可以保留全部，這個上限只是本機的。

**D6. 儲存介面 `KeyStatsStore` 是同步的（local-first）。**
- 內容：`load()`、`saveSession(rows)`、`clear()`，localStorage 實作在 `src/storage/keyStats.ts`。
- 理由：畫面永遠讀本機這一份，遊戲不會因為網路慢或斷線卡住（CLAUDE.md 和 ROADMAP 3.5 都要求斷網不卡住）。
  日後 Supabase 是「同步的對象」：登入後把本機的列上傳、把雲端的列下載回來合併，而不是把這個介面換成非同步的。
- 如果階段 3 決定改成「雲端為主」：需要把介面改成回傳 Promise，並在 `App.tsx` 加載入中的狀態。
